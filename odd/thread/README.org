* Thread

This provides yet another thread pool.

Inspired by:

- Odin's ~thread_pool.odin~
- https://aocoronel.github.io/multicore
- https://www.dgtlgrove.com/p/multi-core-by-default
- https://github.com/aocoronel/aoclibs/blob/main/src/thread.c

** Features

- Enqueue commands from any thread, to any pool.
- Commands are executed by all threads, not just one.
- Provides ~range~ for lock-free iterations.
- Provides ~next_static~ and ~next_dynamic~ for lock-free iterations with work-stealing.
- Set a custom thread ~runner~.

Making a universal library that can beautifully handle all use cases is impossible, or would be extensibly complicated. For example, I've been working on a ~wait~ procedure that can perfeclty wait on all pools, and tell when they are done, but if there is a pool that is independent and can add commands at any time, it requires a different approach, possibly at the user level.

This API tries to be both simple and extensible. Many convenience procedures are available at [[./easy]], but you can use the parts to make your own high level API, accordingly to your specific cases.

** Implementation design

The common job system approach will have a queue, where each thread tries to dequeue, and get a unique command to execute. This had several issues, where many threads are trying to dequeue at the same time; commands have variadic execution times; command are executed out of order; and maybe something else I didn't figure out.

In this pool all threads will run the same command.

The pool contains a queue, allocated with the virtual allocator, avoiding reallocation churn. Appending new commands to the queue uses a mutex lock, but reading a command doesn't. In case, the queue wasn't resetted and it is now full, it will behave like a ring. Each append will broadcast all waiting threads to check the new command(s).

Because all threads execute the same command, performing work-stealing at the user level is very cheap, only requiring a single atomic variable. See the example below. But it doesn't mean that all threads will actually run all commands, because they will also attempt to steal the command from other threads. This takes it very close to ordered command execution, without unnecessary waiting from the threads that already did their part.

Because we treat everything as a command, even to reset the state of the pool or to shut it down is done through a command.

Most importantly, the Pool implementation easily allows threads to enqueue commands not only to theirselves, but also to another pool.

** Take a taste

Note: this example isn't really faster than a single thread one, but it works.

A runnable example is at [[../../examples/]].

#+BEGIN_SRC odin
  // A small wrapper to rc_thread, for type safety
  rc :: proc(
  	pool: ^othread.Pool,
  	files: []os.File_Info,
  	allocator := context.temp_allocator,
  ) {
  	context.allocator = allocator
  	files_ptr := new([]os.File_Info)
  	files_ptr^ = files
  	ethread.add_command(pool, rc_thread, files_ptr, new(int))
  }

  // Print all files in directory, recursively
  rc_thread :: proc(args: []rawptr) {
  	files := cast(^[]os.File_Info)args[0]
  	commands := cast(^int)args[1]

  	name, _ := thread.get_name()

  	for i in othread.next(commands, len(files)) {
  		f := files[i]
  		if f.type == .Directory {
  			fs, err := os.read_directory_by_path(f.fullpath, -1, context.temp_allocator)
  			if err != nil {
  				continue
  			}
  			rc(othread.get_context_pool(), fs)
  		} else {
  			fmt.println(name, f.fullpath)
  		}
  	}
  }
#+END_SRC
